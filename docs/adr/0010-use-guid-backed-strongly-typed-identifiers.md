# ADR-0010: Use GUID-backed strongly typed identifiers

## Context

The legacy identifier strategy, recorded as [ADR-0009](0009-use-ulid-based-strongly-typed-identifiers.md), prescribed ULIDs stored as strings and generated on clients to support offline mobile clients. The implementation never followed it. Checked against the code on 2026-10-01:

- every aggregate and entity identifier is a `readonly record struct` wrapping a `Guid`, with `New()` calling `Guid.NewGuid()` and `From(Guid)`;
- PostgreSQL stores identifiers as `uuid` through EF Core value conversions, from the first migration onwards;
- `DomusMind.Contracts` types identifiers as `Guid`, and routes constrain them with `{id:guid}`;
- no ULID library is referenced on any platform;
- most create commands generate the identifier on the server, while the Meal Planning create commands (meal plan, recipe, weekly template, copy previous week) accept a GUID generated by the web app;
- there is no mobile client and no offline mode in the repository.

Leaving ADR-0009 as the only identifier record made the documentation and agent context describe a format the system does not use. Moving to ULID would change every key and foreign key column, every contract, every route constraint and the web client types, and would need a data migration on every self-hosted installation. The product owner delegated this decision to the architecture review of the documentation migration (October 2026), which took it from the evidence above.

## Decision

We will keep identifying each aggregate and entity with its own strongly typed identifier, a `readonly record struct` wrapping a `Guid`, stored as PostgreSQL `uuid` and exchanged as a GUID in the API.

Strong typing is the part that carries the architectural weight: identifiers of different aggregates cannot be mixed up at compile time, they are immutable, and they encode no mutable information. GUID is kept as the format because it is what every table, contract, route and installed database already uses, and because the driver that motivated ULID, coordination-free generation on offline mobile clients, does not exist in the system. This record does not change who generates identifiers; that remains a per-slice choice as described above.

## Consequences

- **Positive:** No migration of schemas, contracts or installed databases. Native `uuid` columns are compact and indexed efficiently. GUIDs are supported natively by .NET, Npgsql and browsers (`crypto.randomUUID`), so a client can still supply an identifier where a slice allows it.
- **Negative:** `Guid.NewGuid()` produces random version 4 UUIDs, which are not sortable by creation time and give poorer index locality on large tables; ordering by creation needs a timestamp column.
- **Neutral:** If creation-time ordering becomes necessary, .NET's `Guid.CreateVersion7()` yields time-ordered UUIDs with the same `uuid` storage and contracts, and can be adopted inside each `New()` without a schema or contract change; that is a revisit option, not part of this decision. `openspec/config.yaml` still describes ULID-based identifiers as proposed by ADR-0009 and must be aligned with this record.

## Alternatives considered

- **Migrate to ULID as ADR-0009 prescribed**: rejected because it changes every key, contract and installed database for a benefit (offline client-side generation, shorter text form) that no current client needs.
- **Adopt UUID version 7 now**: not adopted because nothing in the system orders by identifier today; it stays available later without a contract change.
- **Primitive, untyped `Guid` identifiers**: rejected because they lose the compile-time separation between aggregates that the code already has.
